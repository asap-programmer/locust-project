## 1. Описание тестируемых приложений

### 1.1 Архитектура системы

Тестируемая система представляет собой два варианта реализации сервиса глоссария блокчейн-терминов:

1. **REST API** на базе FastAPI
2. **gRPC сервис** на базе grpcio

Оба приложения используют:
- **База данных:** SQLite (файл `glossary.db`)
- **ORM:** SQLAlchemy 2.0
- **Количество записей:** 12 предзаполненных терминов

### 1.2 Используемые технологии

| Компонент | REST | gRPC |
|-----------|------|------|
| Фреймворк | FastAPI 0.115.6 | grpcio 1.60.0 |
| Сервер | Uvicorn 0.34.0 | ThreadPoolExecutor |
| Сериализация | JSON (Pydantic) | Protocol Buffers 4.25 |
| Протокол | HTTP/1.1 | HTTP/2 |

### 1.3 API эндпоинты

| Операция | REST Endpoint | gRPC Method |
|----------|---------------|-------------|
| Получить все термины | GET /terms | GetAllTerms |
| Получить термин | GET /terms/{keyword} | GetTerm |
| Создать термин | POST /terms | CreateTerm |
| Обновить термин | PUT /terms/{keyword} | UpdateTerm |
| Удалить термин | DELETE /terms/{keyword} | DeleteTerm |
| Получить категории | GET /categories | GetCategories |
| Проверка здоровья | GET /health | HealthCheck |

### 1.4 Данные для запросов

**Для создания термина (POST/CreateTerm):**
```json
{
    "keyword": "Название термина (1-200 символов, уникальный)",
    "definition": "Определение термина (минимум 10 символов)",
    "category": "Категория (опционально)"
}
```

**Для обновления термина (PUT/UpdateTerm):**
```json
{
    "definition": "Новое определение (опционально)",
    "category": "Новая категория (опционально)"
}
```

## 3. Тестовые сценарии

### 3.1 Сценарий: Sanity Check (Лёгкая нагрузка)

**Цель:** Проверка базовой работоспособности системы

**Конфигурация:**
| Параметр | Значение |
|----------|----------|
| Пользователей | 5 |
| Spawn Rate | 1/s |
| Длительность | 1 минута |

**Логика поведения пользователя:**
- 90% операции чтения (GET /terms, GET /terms/{keyword})
- 10% операции записи (POST, PUT, DELETE)
- Пауза между запросами: 1-3 секунды

**Гипотеза:**
Система должна работать стабильно, без ошибок. Ожидаемое время отклика < 500ms.

**Фрагмент кода теста:**
```python
@task(10)
def get_all_terms(self):
    """Получение всех терминов (высокий приоритет)"""
    self.client.get("/terms", name="GET /terms")

@task(8)
def get_term_by_keyword(self):
    """Получение термина по ключу"""
    keyword = random.choice(EXISTING_KEYWORDS)
    self.client.get(f"/terms/{keyword}", name="GET /terms/{keyword}")
```

### 6.2 Рекомендации по оптимизации

1. **Для REST API:**
   - Использовать асинхронную работу с БД
   - Добавить кэширование для частых запросов
   - Рассмотреть connection pooling

2. **Для gRPC:**
   - Увеличить размер пула потоков
   - Оптимизировать сериализацию
   - Использовать streaming для больших данных

3. **Общие рекомендации:**
   - Заменить SQLite на PostgreSQL для продакшена
   - Добавить индексы на часто используемые поля
   - Использовать горизонтальное масштабирование

### 6.3 Возможные улучшения эксперимента

1. Проведение тестов на отдельных машинах (клиент/сервер)
2. Тестирование с реальной сетевой задержкой
3. Добавление тестов с различными размерами данных
4. Использование PostgreSQL вместо SQLite
5. Тестирование с несколькими воркерами Locust

### 6.4 Ограничения тестирования

1. **Локальная среда** - отсутствие реальной сетевой задержки
2. **SQLite** - не отражает реальные production-сценарии с РСУБД
3. **Малый объём данных** - 12 записей не показывают масштабирование БД
4. **Один инстанс** - не тестировалась горизонтальная масштабируемость
5. **Loopback** - отсутствие влияния сетевого стека

### 7.2 Резюме исследований

#### Общие выводы из литературы:

1. **gRPC превосходит REST по производительности на 20-50%** в большинстве сценариев
   - Бинарная сериализация эффективнее JSON
   - HTTP/2 мультиплексирование снижает overhead

2. **REST остаётся предпочтительным для:**
   - Публичных API (лучшая совместимость)
   - Простых CRUD операций
   - Браузерных приложений

3. **gRPC рекомендуется для:**
   - Внутренней коммуникации микросервисов
   - Высоконагруженных систем
   - Real-time приложений
   - Мобильных приложений (экономия трафика)

4. **GraphQL занимает нишу:**
   - Сложные запросы с множеством связей
   - Оптимизация трафика (запрос только нужных полей)
   - Агрегация из нескольких источников
