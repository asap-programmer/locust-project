# Отчёт о нагрузочном тестировании: REST vs gRPC

**Проект:** Глоссарий блокчейн-терминов
**Дата проведения:** 07.01.2026
**Инструмент:** Locust 2.20+

---

## 1. Описание тестируемых приложений

### 1.1 Архитектура системы

Тестируемая система представляет собой два варианта реализации сервиса глоссария блокчейн-терминов:

1. **REST API** на базе FastAPI
2. **gRPC сервис** на базе grpcio

```
┌─────────────────┐     ┌─────────────────┐
│   Locust        │     │   Locust        │
│   REST Client   │     │   gRPC Client   │
└────────┬────────┘     └────────┬────────┘
         │ HTTP/JSON             │ HTTP/2 + Protobuf
         ▼                       ▼
┌─────────────────┐     ┌─────────────────┐
│   FastAPI       │     │   gRPC Server   │
│   REST API      │     │   (Python)      │
│   Port: 8000    │     │   Port: 50051   │
└────────┬────────┘     └────────┬────────┘
         │                       │
         ▼                       ▼
┌─────────────────────────────────────────┐
│              SQLite Database            │
│              (glossary.db)              │
└─────────────────────────────────────────┘
```

Оба приложения используют:
- **База данных:** SQLite (файл `glossary.db`)
- **ORM:** SQLAlchemy 2.0
- **Количество записей:** 12 предзаполненных терминов блокчейн-тематики

### 1.2 Используемые технологии

| Компонент | REST | gRPC |
|-----------|------|------|
| Фреймворк | FastAPI 0.115.6 | grpcio 1.60.0 |
| Сервер | Uvicorn 0.34.0 | ThreadPoolExecutor (10 workers) |
| Сериализация | JSON (Pydantic 2.8.2) | Protocol Buffers 4.25.1 |
| Протокол | HTTP/1.1 | HTTP/2 |
| Валидация | Pydantic схемы | Proto-определения |

### 1.3 API эндпоинты

| Операция | REST Endpoint | gRPC Method | Трудоёмкость |
|----------|---------------|-------------|--------------|
| Получить все термины | GET /terms | GetAllTerms | Средняя (выборка из БД) |
| Получить термин | GET /terms/{keyword} | GetTerm | Низкая (поиск по индексу) |
| Создать термин | POST /terms | CreateTerm | Высокая (INSERT + валидация) |
| Обновить термин | PUT /terms/{keyword} | UpdateTerm | Средняя (UPDATE) |
| Удалить термин | DELETE /terms/{keyword} | DeleteTerm | Средняя (DELETE) |
| Получить категории | GET /categories | GetCategories | Низкая |
| Проверка здоровья | GET /health | HealthCheck | Минимальная |

### 1.4 Данные для запросов

**Структура термина в базе данных:**

| Поле | Тип | Описание |
|------|-----|----------|
| id | INTEGER | Первичный ключ (AUTO INCREMENT) |
| keyword | VARCHAR(200) | Ключевое слово (UNIQUE, INDEX) |
| definition | TEXT | Определение термина |
| category | VARCHAR(100) | Категория (INDEX) |
| created_at | DATETIME | Дата создания |
| updated_at | DATETIME | Дата обновления |

**Для создания термина (POST /terms или CreateTerm):**
```json
{
    "keyword": "Название термина (1-200 символов, уникальный)",
    "definition": "Определение термина (минимум 10 символов)",
    "category": "Категория (опционально)"
}
```

**Пример ответа GET /terms:**
```json
[
    {
        "id": 1,
        "keyword": "Blockchain",
        "definition": "Распределенная база данных...",
        "category": "Основные понятия",
        "created_at": "2025-10-17T10:18:50",
        "updated_at": "2026-01-07T12:54:47"
    }
]
```

## 3. Тестовые сценарии

### 3.1 Сценарий: Sanity Check (Лёгкая нагрузка)

**Цель:** Проверка базовой работоспособности системы

**Конфигурация:**
| Параметр | Значение |
|----------|----------|
| Пользователей | 5 |
| Spawn Rate | 1/s |
| Длительность | 1 минута |

**Логика поведения пользователя (веса задач):**
```
GET /terms (все термины)        ████████████████ 10
GET /terms/{keyword}            █████████████ 8
GET /terms?pagination           ███████ 5
GET /terms?category             ██████ 4
GET /categories                 ████ 3
GET /health                     ███ 2
POST /terms (создание)          ███ 2
PUT /terms/{keyword}            ██ 1
DELETE /terms/{keyword}         ██ 1
```

Соотношение операций: **~90% чтение / ~10% запись**

**Гипотеза:** Система должна работать стабильно, без ошибок. Ожидаемое время отклика < 500ms.

**Фрагмент кода теста (REST):**
```python
class GlossaryRESTUser(HttpUser):
    wait_time = between(1, 3)

    @task(10)
    def get_all_terms(self):
        """Получение всех терминов (высокий приоритет)"""
        self.client.get("/terms", name="GET /terms")

    @task(8)
    def get_term_by_keyword(self):
        """Получение термина по ключу"""
        keyword = random.choice(EXISTING_KEYWORDS)
        self.client.get(f"/terms/{keyword}", name="GET /terms/{keyword}")

    @task(2)
    def create_term(self):
        """Создание нового термина"""
        term_data = generate_term_data()
        self.client.post("/terms", json=term_data, name="POST /terms")
```

### 4.3 Анализ результатов

#### 4.3.1 Точка деградации

**REST API:**
- **Начало деградации:** ~50-100 пользователей
- **Признаки:** Резкий рост латентности (с 28ms до 3000ms), падение RPS, появление таймаутов (p99 = 90 сек)
- **Причина:** Синхронная обработка, накопление очереди запросов

**gRPC:**
- **Начало деградации:** Не выявлена в рамках тестов (до 200 пользователей)
- **Признаки:** Небольшой рост латентности при peak (с 8ms до 23ms)
- **Причина:** HTTP/2 мультиплексирование эффективно распределяет нагрузку

#### 4.3.2 Изменение латентности при росте нагрузки

| Пользователей | REST Avg (ms) | gRPC Avg (ms) | Разница |
|---------------|---------------|---------------|---------|
| 5 | 20.19 | 10.14 | gRPC в 2x быстрее |
| 20 | 27.80 | 9.07 | gRPC в 3x быстрее |
| 30 | 51.36 | 20.74 | gRPC в 2.5x быстрее |
| 100 | **3,021** | 7.63 | **gRPC в 396x быстрее** |
| 200 | 341.86 | 22.81 | gRPC в 15x быстрее |

```
Латентность (ms) - логарифмическая шкала:

gRPC:  ██ 10 → █ 9 → ███ 21 → █ 8 → ███ 23

       5u       20u       30u        100u (stress)                              200u (peak)
```

#### 4.3.3 Бутылочные горлышки

**Выявленные ограничения:**

1. **SQLite**
   - Однопоточная запись
   - Блокировки при конкурентном доступе
   - Особенно влияет на REST при высокой нагрузке

2. **REST/HTTP/1.1**
   - Отдельное TCP соединение для каждого запроса
   - JSON сериализация/десериализация
   - Текстовый протокол с overhead на headers

3. **FastAPI + Uvicorn**
   - Асинхронный, но SQLAlchemy работает синхронно
   - Накопление очереди при высокой нагрузке

4. **gRPC преимущества**
   - HTTP/2 мультиплексирование
   - Бинарный протокол (меньше данных)
   - Переиспользование соединений
   - ThreadPoolExecutor эффективно распараллеливает

## 5. Сравнение REST vs gRPC

### 5.1 Численное сравнение латентности

### 5.2 Сравнение RPS

| Сценарий | REST RPS | gRPC RPS | Разница |
|----------|----------|----------|---------|
| Sanity | 4.23 | 4.36 | +3% |
| Normal | 18.52 | 18.98 | +2% |

| Peak | 47.13 | 43.44 | -8% |

**Вывод:** При низкой/средней нагрузке RPS сопоставим, но при stress-тесте gRPC показывает **в 11 раз больше RPS**.

### 5.3 Анализ Overhead

| Аспект | REST (JSON/HTTP) | gRPC (Protobuf/HTTP2) | Комментарий |
|--------|------------------|----------------------|-------------|
| Размер типичного ответа | ~500-2000 bytes | ~200-800 bytes | Protobuf компактнее на 50-70% |
| Время сериализации | Выше | Ниже | JSON parsing vs binary |
| Соединения | Connection per request* | Мультиплексирование | HTTP/2 переиспользует соединения |
| Headers overhead | Текстовые, ~200-500 bytes | Бинарные, сжатые | HPACK сжатие в HTTP/2 |
| Типизация | Runtime (Pydantic) | Compile-time (proto) | gRPC выявляет ошибки раньше |

*FastAPI/Uvicorn поддерживает keep-alive, но HTTP/1.1 всё равно менее эффективен

## 6. Выводы

### 6.1 Основные выводы

1. **Производительность gRPC vs REST:**
   - При **низкой нагрузке** (5-20 users): gRPC быстрее в **2-3 раза** по латентности
   - При **высокой нагрузке** (100 users): gRPC быстрее в **~400 раз** по латентности и в **11 раз** по RPS
   - gRPC показывает **стабильную латентность** независимо от нагрузки (7-23ms)
   - REST **деградирует экспоненциально** при росте нагрузки

2. **Масштабируемость:**
   - REST: эффективен до ~30-50 concurrent users
   - gRPC: справляется с 200+ users без существенной деградации

3. **Стабильность:**
   - Оба сервиса стабильны при умеренной нагрузке (10 минут, 30 users)
   - gRPC: 0 ошибок во всех сценариях
   - REST: 3 ошибки при stress-тесте (таймауты)

4. **Точка деградации:**
   - REST: ~50-100 пользователей
   - gRPC: не достигнута (>200 пользователей)

### 6.2 Рекомендации по оптимизации

**Для REST API:**
1. Использовать асинхронную работу с БД (asyncpg, databases)
2. Добавить кэширование для частых запросов (Redis)
3. Увеличить количество workers Uvicorn
4. Рассмотреть connection pooling
5. Оптимизировать JSON сериализацию (orjson)

**Для gRPC:**
1. Увеличить размер ThreadPoolExecutor (> 10 workers)
2. Использовать streaming для больших данных
3. Настроить keepalive параметры
4. Рассмотреть асинхронный сервер (grpcio-asyncio)

**Общие рекомендации:**
1. **Заменить SQLite на PostgreSQL** для продакшена — это главное бутылочное горлышко
2. Добавить индексы на часто используемые поля
3. Использовать горизонтальное масштабирование (несколько инстансов)
4. Добавить мониторинг (Prometheus + Grafana)

### 6.3 Возможные улучшения эксперимента

1. Проведение тестов на отдельных машинах (клиент/сервер)
2. Тестирование с реальной сетевой задержкой
3. Добавление тестов с различными размерами данных (100, 1000, 10000 записей)
4. Использование PostgreSQL вместо SQLite
5. Тестирование с несколькими воркерами Locust (distributed mode)
6. Профилирование CPU/Memory во время тестов
7. Тестирование streaming gRPC

### 6.4 Ограничения проведённого тестирования

1. **Локальная среда** — отсутствие реальной сетевой задержки (loopback ~0ms)
2. **SQLite** — не отражает реальные production-сценарии с РСУБД
3. **Малый объём данных** — 12 записей не показывают масштабирование БД
4. **Один инстанс** — не тестировалась горизонтальная масштабируемость
5. **Один клиент Locust** — не distributed mode
6. **Отсутствие внешних зависимостей** — нет сетевых вызовов к другим сервисам

### 6.5 Когда использовать REST vs gRPC

| Критерий | Рекомендация |
|----------|-------------|
| Публичный API | REST (совместимость с браузерами) |
| Внутренние микросервисы | gRPC (производительность) |
| Высокая нагрузка (>50 RPS) | gRPC |
| Простой CRUD | REST (проще разработка) |
| Real-time / Streaming | gRPC |
| Мобильные приложения | gRPC (экономия трафика) |
| Браузерный клиент | REST или gRPC-Web |

### 7.2 Резюме исследований

#### Общие выводы из литературы:

1. **gRPC превосходит REST по производительности на 30-70%** в большинстве сценариев
   - Бинарная сериализация (Protobuf) эффективнее JSON в 2-3 раза
   - HTTP/2 мультиплексирование снижает overhead
   - Меньше данных передаётся по сети

2. **REST остаётся предпочтительным для:**
   - Публичных API (совместимость с браузерами)
   - Простых CRUD операций
   - Быстрого прототипирования
   - Когда важна человекочитаемость (debugging)

3. **gRPC рекомендуется для:**
   - Внутренней коммуникации микросервисов
   - Высоконагруженных систем (>100 RPS)
   - Real-time приложений
   - Мобильных приложений (экономия трафика и батареи)
   - Когда важна строгая типизация

4. **GraphQL занимает свою нишу:**
   - Сложные запросы с множеством связей
   - Оптимизация трафика (запрос только нужных полей)
   - Backend-for-Frontend (BFF) паттерн
   - Агрегация из нескольких источников

```bash
python run_tests.py -s all -t both

python analyze_results.py --charts
```
